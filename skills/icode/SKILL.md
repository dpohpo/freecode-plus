## 第一部分：反幻觉铁律（5 原则 — 全局底线）

### 原则 1: 诚信原则 — 不知道就说不知道

**[HARD]** 不知道的事情说「我不知道」。不确定的事情说「我不确定」。禁止编造。
- 生效条件：所有场景，无例外
- 失效条件：无（此原则不可豁免）
- 验证方法：删掉回答中所有不确定的部分，剩下的应该全是真的

### 原则 2: 实事求是原则 — 证明之前先保持怀疑

**[HARD]** 对任何外部事实性声明，在被证实之前默认视为「未验证」。
- 事实优先于直觉、权威、流行观点
- 禁止用自身训练知识「验证」自身训练知识（自证无效）
- 有效验证来源：官方文档（WebSearch/WebFetch）、当前环境实际执行、用户提供的一手信息
- 生效条件：任何涉及外部工具/API/平台/服务的事实声明
- 失效条件：纯逻辑/数学推导（前提为真则结论必然为真）

### 原则 3: 98% 置信度门槛

**[HARD]** 置信度低于 98% 的外部事实，禁止用确定性语气表达。

| 置信度 | 允许的表达方式 |
|--------|--------------|
| ≥ 98% (VERIFIED) | 直接陈述，附验证来源 |
| 80-97% (HIGH_CONFIDENCE) | 「根据我的知识……但建议验证」 |
| 50-79% (UNCERTAIN) | 「我不确定，但可能是……需要验证」 |
| < 50% (SPECULATIVE) | 「这是推测，很可能不准确」 |

- 生效条件：所有对外部事物的技术声明
- 失效条件：用户明确要求快速草稿/头脑风暴模式
- **铁律中的铁律：永远不说 "should work" — 要么已验证，要么说没验证**

### 原则 4: 失效条件必标原则

**[HARD]** 任何技术性声明必须标注失效条件。

```
[声明内容]
  生效条件：……
  失效条件：……
  验证方法：……
```

- 生效条件：涉及版本、平台、配置、环境的技术声明
- 失效条件：普适性极强的声明（如「1+1=2」）

### 原则 5: 代码交付铁律

**[HARD]** 写代码时，所有外部依赖必须验证真实性：

| 检查项 | 验证方法 | 未验证时 |
|--------|---------|---------|
| import/require 的包名 | `pip show` / `npm info` / 官方文档 | 标注 `⚠️ UNVERIFIED` |
| API 函数签名 | 官方 API reference | 标注 `⚠️ UNVERIFIED` |
| CLI 命令和 flag | `--help` 或官方文档 | 标注 `⚠️ UNVERIFIED` |
| 配置项 key 名称 | 官方文档 | 标注 `⚠️ UNVERIFIED` |
| 异常/错误类型 | 语言/框架文档 | 标注 `⚠️ UNVERIFIED` |

**幻觉高危区**（默认置信度降一级，必须额外验证）：
1. 新工具/新框架 API
2. CLI 子命令和 flag
3. 配置文件 key 名称
4. 错误码/异常类型
5. 第三方服务限制/配额
6. 跨平台差异

## 第二部分：零幻觉编码系统（4 阶段执行）

### 阶段零：外部声明全量扫描

接到编码任务后，**先扫描再动手**。主动识别代码中所有外部引用：

| 类别 | 识别特征 | 示例 |
|------|---------|------|
| 包/库 | import/require/pip/npm | `import pandas`, `require('express')` |
| API 函数 | 外部库的方法调用 | `pd.DataFrame()`, `app.listen()` |
| CLI 命令 | shell 调用 | `docker compose up`, `gh pr create` |
| 配置项 | config key/env var | `DATABASE_URL`, `port: 3000` |
| 类型/协议 | 外部类型引用 | `HttpResponse`, `WebSocket` |
| 端点/URL | 外部服务地址 | `api.stripe.com/v1/charges` |

**判定标准：如果该标识符的源头定义不在当前项目内，它就是外部声明，必须走验证管线。**

输出扫描结果：

```
📡 外部声明扫描报告
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
│ #  │ 声明           │ 类别   │ 状态       │
│────│───────────────│───────│───────────│
│ 1  │ pandas v2.x    │ 包/库  │ 待验证     │
│ 2  │ pd.read_csv()  │ API   │ 待验证     │
│ …  │ …              │ …     │ …         │
```

### 阶段一：验证管线（Verify Pipeline）— 98% 置信度门槛

对每个外部声明，执行**双轨三轮**验证：

**轮次 1：网络验证（理论层）**

| 步骤 | 方法 | 目标 |
|------|------|------|
| 1a | WebSearch 搜索 `[包名/API] official documentation [当前年份]` | 找到官方文档 |
| 1b | WebFetch 抓取官方文档页面 | 确认函数签名、参数、返回值 |
| 1c | 溯源检查：来源是官方 repo/PyPI/npm/docs？ | 排除 AI 生成的假文档 |

网络验证通过标准：来源为官方一手资料 + 函数签名完全匹配 + 版本号明确

**轮次 2：执行验证（事实层）**

| 步骤 | 方法 | 目标 |
|------|------|------|
| 2a | `pip show [包]` / `npm info [包]` / `which [cmd]` | 确认当前环境已安装 |
| 2b | 最小代码片段实际运行 | 确认函数可调用、返回值类型正确 |
| 2c | 边界测试（空输入、异常输入） | 确认行为符合文档 |

**轮次 3：交叉对齐**

| 网络结果 | 执行结果 | 判定 | 动作 |
|---------|---------|------|------|
| 存在 + 签名匹配 | 运行成功 | **VERIFIED (≥98%)** | 写入技能库 |
| 存在 + 签名匹配 | 运行失败 | **VERSION_MISMATCH** | 查版本差异，修正后重验 |
| 找不到 | 运行成功 | **LOCAL_ONLY** | 标注为本地/私有包，提醒用户 |
| 找不到 | 运行失败 | **NOT_EXIST** | 进入阶段二（创造管线） |

### 阶段二：创造管线（Create Pipeline）— 100% 置信度门槛

当阶段一判定 NOT_EXIST 时启动。

**步骤 2.1：确认「不存在」是事实（TruthSeek 三轮搜索）**

| 轮次 | 搜索内容 | 目的 |
|------|---------|------|
| 第一轮 | 直接搜索功能名/库名 | 确认确实不存在 |
| 第二轮 | 搜索替代方案/类似功能 | 确认没有已有替代品 |
| 第三轮 | 搜索「为什么没有 X」 | 理解原因：需求小众、技术限制、还是有替代路径 |

如果找到替代方案 → 回阶段一验证替代方案，不进入创造。

**步骤 2.2：第一性原理下钻（Deepest 模式）**

```
[需要的功能]
  ↓ 它本质上在做什么？
[底层操作]
  ↓ 这个操作依赖什么？
[语言/OS 级原语]
  ↓ 这些原语是否 VERIFIED？
[已验证的基础层]
```

**铁律：构建链条中的每一层都必须是 VERIFIED 的。不允许在未验证的中间层上构建。**

**步骤 2.3：底层实现**

1. 定义接口（输入/输出/异常）
2. 用最底层可用的已验证 API 实现
3. 每个函数写 docstring + 类型标注
4. 写至少 3 个测试用例（正常/边界/异常）

**步骤 2.4：三轨交叉验证 → 100%**

| 验证轨道 | 方法 | 通过标准 |
|---------|------|---------|
| 理论轨（Hypothesis） | 逻辑推导：输入→处理→输出的每一步是否必然正确？ | 找不到反例 |
| 实践轨（Execution） | 实际运行全部测试用例 | 全部通过 |
| 交叉对齐 | 理论预测的行为 vs 实际行为是否完全一致？ | 零偏差 |

**三轨全部通过 = 100% 置信度。缺任何一条 → 不纳入技能库，标注为 DRAFT。**

### 阶段三：编码执行

在阶段零、一、二完成后，所有外部依赖已确认，开始写代码：

1. **只使用 VERIFIED 或 TRIPLE_VERIFIED 的外部声明**
2. 每个 import 旁标注验证状态：`import pandas  # VERIFIED: v2.2.0, PyPI official`
3. 未验证项禁止使用，或标注 `# ⚠️ UNVERIFIED`
4. 代码完成后，重新扫描确认无遗漏的外部引用

## 第三部分：编码 8 铁律 + 交付自审

### 8 铁律

1. **先扫描后编码** — 动手写代码之前，必须完成外部声明全量扫描（6类：包/API/CLI/配置/类型/端点）
2. **双轨验证不可省** — 网络验证（官方文档）+ 执行验证（实际运行），缺一不可
3. **溯源到一手** — 官方 repo/PyPI/npm/docs 才算一手资料，博客/AI 转述不算
4. **98% 是底线** — 置信度低于 98% 的外部声明禁止以确定性语气写入代码
5. **100% 是创造的门槛** — 自建不存在的功能必须三轨全通过（理论推导 + 实际执行 + 交叉对齐）
6. **构建链每层必须 VERIFIED** — 不允许在未验证的中间层上构建
7. **失效条件必标** — 每个验证通过项都必须写明什么条件下失效
8. **「不存在」要三轮证明** — 直接搜索 + 替代方案搜索 + 原因搜索，三轮都无结果才确认不存在

### 交付自审清单

```
□ 阶段零扫描完成，所有外部声明已识别
□ 阶段一验证完成，所有已有依赖 ≥ 98% VERIFIED
□ 阶段二创造完成（如有），自建功能 100% TRIPLE_VERIFIED
□ 代码中无未标注的外部引用
□ 所有技术声明含生效/失效/验证条件三元组
□ 没有使用 "should work"
```

## 最终步：知识沉淀 + 蒸馏

编码任务完成后，判断是否值得存入知识库：

**存入条件**（满足任一）：
- 验证过程中发现重要的 API 变更或弃用
- 自建了不存在的功能
- 交叉验证中发现网络 vs 执行冲突
- 排查超过 3 轮对话
- 涉及配置/权限/环境等易忘细节
- 根因反直觉（表象 ≠ 真因）
- 用户要求存入

**不存条件：** 一句话能答的简单问题 | 纯知识查询 | 无复用价值

**执行流程：**
1. 主动问用户：「要存入知识库吗？」
2. 若是 → 生成完整版写入 `~/.claude/knowledge/YYYY-MM-DD-<关键词>.md`
3. 立即执行五层蒸馏（L1清除装饰→L2电报体→L3结构压缩→L4语义去重→L5可推导裁剪）
4. 蒸馏版写入 `~/.claude/knowledge/YYYY-MM-DD-<关键词>.distilled.md`（目标 ≤ 原文25%）
5. 输出：`📄 完整版：XXX 字符 ⚗️ 蒸馏版：YYY 字符（压缩率 ZZ%）`

**质量红线：**
- **绝对不删**：错误码、端口号、费率、版本号、关键命令、文件路径
- **绝对不删**：反直觉的发现
- **绝对不删**：踩坑记录中容易重蹈覆辙的坑
- **可以删**：过程性描述、常识性解释、重复信息、装饰性内容

**双版本铁律：完整版用于人类阅读和回溯，蒸馏版用于 AI 快速检索加载。两版必须同时生成，缺一不可。永远不要用蒸馏版覆盖完整版。**
