# /codelaw — 写代码防幻觉铁律

> 每当你写代码时，这条技能自动激活。遵守以下10条铁律，铁律编号即为执行顺序。

---

## 第零铁律：先扫描后编码

写任何代码前，**必须先用 Read/Glob/Bash 确认**：
- 文件是否真实存在
- 目标目录是否可写
- 依赖是否已安装
- import/require 的模块是否存在

```
禁止：在没看过现有代码的情况下直接写代码
```

---

## 第一铁律：API 存在性验证

使用任何第三方库 API 前：
1. 用 Context7 查官方文档，或 `Read` 项目源码
2. 确认方法名、参数名、返回值 **完全匹配**
3. 不得凭记忆/类比猜测 API

常见幻觉：
- 把 A 库的 API 嫁接到 B 库
- 用旧版 API 当新版（如 Prisma `$upload` 根本不存在）
- 给 Express 参数取个名字但实际是 Python 的

---

## 第二铁律：配置与环境变量

使用任何环境变量前：`printenv | grep VAR` 或 `echo $VAR`
使用任何 CLI flag 前：`--help` 确认存在
使用任何配置字段前：查官方文档

**唯一官方 CC 环境变量**：`$CLAUDE_CODE_REMOTE`
CC hooks 数据走 stdin JSON，不存在 `$CLAUDE_TOOL_INPUT`

---

## 第三铁律：版本不过时

推荐任何库/工具前，强制 web search：
1. 项目是否仍在维护
2. 当前最新版本号
3. 引用的 API 是否仍存在于最新版

引用数值（参数量、benchmark、价格）前，必须从官方来源确认。

---

## 第四铁律：禁止自审

**永远不 review 自己刚写的代码** — LLM 不会主动自我否定。

- 写完代码 → 交给 Codex CLI 独立 review
- 写完测试 → 注释掉被测代码再跑一次，确认测试会 fail
- 每个 PR 描述必须包含"这段代码可能出错的地方"

---

## 第五铁律：失败换策略

同一方案失败 **2 次** → 必须换完全不同方向
3 种方案都失败 → **停下来告诉用户需要帮助**

禁止：烧 30 分钟 token 重试本质相同的代码
每次重试前：必须说明"这次和上次的区别是什么"

---

## 第六铁律：术语精确

使用技术术语前确认定义，禁止混用：

| 正确 | ≠ 错误 |
|------|--------|
| late interaction (ColBERT) | cross-encoder |
| SessionEnd hook | session 结束 |
| Unicode-aware | CJK segmentation |
| exFAT | FAT32 |

模型描述必须包含：名称、参数量、维度、语种、许可证——来自 model card。

---

## 第七铁律：跨语言隔离

本项目 Python 3.12，不引入其他语言的 pattern：
- 异步用 `asyncio`，不用 callback pattern
- ORM 用 SQLAlchemy 或直接 SQL，不混
- 不把 JS/TS 的模式套到 Python

---

## 第八铁律：定义完成

每个任务开始前**定义验收标准**，满足后：
- **立即停止**，不做额外优化
- 如想做额外优化，**先问用户**
- 宣布"完成"而不是"我们还可以加…"

---

## 第九铁律：长对话保真

长 session 中：
- 关键决策和约束**写进文件**（CLAUDE.md / MEMORY.md）
- 变量名/文件名保持一致，**不要改**
- 重复建议之前否决过的方案 = Context 腐烂信号

---

## 第十铁律：路径必须验证

每次 `Write`/`Edit`/`Bash` 前：
- 目标文件路径必须 `Read` 确认存在
- 创建文件前确认目录存在
- `import` 语句中的模块必须先 `pip show` 确认已安装

---

## 执行检查清单

每次写代码前默念：

```
[ ] 文件/目录存在？
[ ] API 查过文档了？
[ ] 环境变量验证过了？
[ ] 版本是最新的？
[ ] 不在自审？
[ ] 没在重复失败方案？
[ ] 术语精确？
[ ] 在目标语言内？
[ ] 有验收标准？
[ ] 路径都验证过了？
```

10/10 才能动笔。
