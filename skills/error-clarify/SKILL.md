# Error Clarify - 错误澄清与预防系统

系统性错误记录、分类、分析与预防。每次犯错后运行此技能，确保不再重蹈覆辙。

## 核心原则

> **不记录的错误，等于没发生；不分析的错误，必定重犯。**

## MECE 错误分类体系

### 一级分类（5类 - 按阶段）

| 类型 | 定义 | 示例 |
|------|------|------|
| **理解性** | 误解意图、遗漏需求、过度解读 | 用户说"起名字"实际要"注册到 hcom" |
| **逻辑性** | 推理断裂、因果倒置、假设错误 | 既定假设谬误：把 99.99% 当 100% |
| **技术性** | 代码失败、命令错误、环境问题 | hcom hook 递归导致卡死 |
| **事实性** | 与客观现实不符、数据过时 | API 文档过时导致调用失败 |
| **表达性** | 说明不清、格式混乱、术语不当 | 输出格式不符合预期 |

### 二级标签（4个 - 按性质）

| 标签 | 定义 | 示例 |
|------|------|------|
| **[遗漏]** | 缺少必要部分 | 漏检查 hcom 是否已运行 |
| **[偏差]** | 细节有误但方向正确 | 命令参数顺序错误 |
| **[错位]** | 做了不该做的 | 在 hook 中修改系统配置 |
| **[混淆]** | 概念/边界不清 | 混淆"命名"和"注册" |

### 三级根源（4种 - 按来源）

| 根源 | 定义 | 示例 |
|------|------|------|
| **← 认知局限** | 模型能力边界、既定假设谬误 | 把 99.99% 当 100%，忽略边缘 Case |
| **← 上下文丢失** | 记忆/状态问题 | 忘记之前已设置过配置 |
| **← 信息不足** | 用户输入模糊 | "起名字"未说明要"可见" |
| **← 环境变化** | 依赖/配置变更 | hcom auto_subscribe 行为变化 |

### 特殊错误类型

**既定假设谬误**（逻辑性-混淆-认知局限）
- 定义：把"通常成立"（99.99%）当成"永远成立"（100%）
- 症状：忽略边缘 Case，系统在极端情况下崩溃
- 预防：系统性组件（hooks、启动脚本、权限、并发）必须考虑边缘 Case
- 口诀：**"局部功能信任 99%，系统架构怀疑一切"**

## 已记录错误案例

### 案例 1：hcom 死循环

```
技术性[遗漏] ← 环境变化

【发生过程】
1. SessionStart hook 中调用 hcom start
2. hcom 启动新 CLI 进程
3. 新进程的 SessionStart hook 再次执行
4. 无限循环，所有 agents 卡住

【根本原因】
既定假设谬误：假设"hook 执行后正常返回"，忽略了：
- 新进程会继承环境变量（包括 HCOM_AGENT_NAME）
- 新进程启动会再次触发 SessionStart hook
- auto_subscribe = "collision" 导致消息风暴

【预防措施】
1. Hook 中启动可能触发 hook 的进程时，使用锁文件
2. 检测环境变量（HCOM_SESSION、HCOM_AGENT_ID）防止递归
3. TeammateMessage hook 添加速率限制
4. 配置改为 auto_subscribe = "none"

【下次注意】
- 系统性组件（hooks、启动）必须考虑递归风险
- 既定假设要验证，尤其在边缘 Case 中
```

### 案例 2：命名 vs 注册

```
理解性[混淆] ← 信息不足

【发生过程】
1. 用户说"给自己起个名字"
2. 我只创建了名字 "Nexus"，写入 quote.md
3. 用户要求"让别人看见"，才发现需要注册到 hcom
4. koko、rina 真正执行了 hcom start --name <name>

【根本原因】
"起名字"有两种含义：
- 语义层：创建一个标识符
- 系统层：注册到服务发现让其他人可见

混淆了这两层，默认用户只要语义层的名字。

【预防措施】
1. 遇到"命名"、"注册"类需求，确认是否需要服务发现
2. 验证：其他 agent 能否通过 hcom list 看到我？
3. 不确定时，直接问用户

【下次注意】
- "名字"可能只是标识符，也可能是服务注册
- 动手前先验证：这个动作的效果是什么？谁能感知到？
```

### 案例 3：既定假设谬误

```
逻辑性[混淆] ← 认知局限

【发生过程】
1. 假设："hook 执行后正常返回"（99.99% 成立）
2. 在 hook 中调用 hcom start
3. 忽略了 0.01%：新进程会触发递归
4. 系统崩溃

【根本原因】
把"通常成立"当成"永远成立"。忽略了系统性风险：
- Hook、启动脚本、权限、并发 —— 这些场景的边缘 Case 会致命
- 局部功能可以信任 99%，系统架构必须怀疑一切

【预防措施】
1. 系统性组件必须考虑边缘 Case
2. 问自己：什么情况下这个假设不成立？
3. 递归、并发、竞态条件 —— 默认假设它们会发生

【下次注意】
- 局部功能：快速迭代，信任 99%
- 系统架构：怀疑一切，盯着 0.01%
- 口诀：**"hooks 会递归，配置会变化，假设会失效"**
```

## 铁律

1. **每次错误必记录**，不记录等于没发生
2. **分类要准确**，便于后续统计分析
3. **预防要具体**，下次可直接执行
4. **系统性风险**（hooks、启动、权限、并发）必须考虑边缘 Case
